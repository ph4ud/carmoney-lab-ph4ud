# plan_MILEAGE — пробег не больше 400 000 км, иначе решение review

- Дата: 2026-09-24. Автор: planner.
- Задача: при расчёте решения добавить проверку «пробег авто не больше 400 000 км,
  иначе решение `review`».
- Источники: `docs/setup/code_map.md`, scout-сводка по пробегу из
  `docs/setup/agents.md`, `AGENTS.md` (конвенции), исходники `backend/src/Domain/`,
  `backend/config/rules.php`, существующие тесты.
- Код не менялся; этот план — единственный артефакт задачи.

## Как понято правило

- Пробег берётся из заявки (`mileage`, нормализуется валидатором в int 0..500000).
- Если пробег ≤ 400 000 — решение не меняется (чистый LTV-расчёт).
- Если пробег > 400 000 — решение не `approve`: понижается до `review`.
- Порог — число из `backend/config/rules.php`, не хардкод (конвенция AGENTS.md).

## Допущения (нужны подтверждения заказчика — см. Вопросы)

1. **Приоритет reject**: правило гейтит только `approve`. Если по LTV решение
   `reject`, высокий пробег его не смягчает (`reject` остаётся `reject`).
   Буквальное прочтение «иначе решение review» допускает и вариант «ровно
   `review` даже вместо `reject`» — это вопрос 1.
2. **Граница включительно**: «не больше 400 000» = `mileage <= 400000` не
   меняет решение; 400 000 и меньше — правило не срабатывает.
3. **Пустой пробег**: остаётся поведением валидации, а не решения:
   ключа `mileage` нет → `ValidationException` (422); пустое поле формы
   превращается фронтендом в `0` (см. Риски, п. 7).

## 3. Тесты

Граничные значения по пробегу — отдельными строками (порог 400 000,
LTV-зоны: `< 60` approve, `60..85` review, `> 85` reject):

- `mileage 399999` + LTV 50 → `approve` (правило не срабатывает)
- `mileage 400000` + LTV 50 → `approve` (граница включительно)
- `mileage 400001` + LTV 50 → `review` (понижение из approve)
- `mileage 500000` + LTV 50 → `review` (верх валидного диапазона)
- `mileage 400001` + LTV 95 → `reject` (приоритет reject — Допущение 1)
- `mileage 400001` + LTV 75 → `review` (решение и так review, не меняется)
- пустой пробег, ключа нет → `ValidationException` с ошибкой ключа `mileage`
- пустой пробег, пустая строка `''` → валидно, нормализуется в `0` (поведение
  фронтенда: `Number('') === 0`)
- `mileage 500001` → `ValidationException` (`max_mileage_km` не тронут)
- `ltv 60.0` + низкий пробег → `review` — пин текущей LTV-границы `<` (см.
  Риски, п. 4; докблок ей противоречит)

Размещение:

- `DecisionEngineTest` — все строки выше, кроме «пустой» и `500001` (это
  валидатор); провайдер `ltvValues` получает вторую колонку.
- `AssessmentServiceTest` — сквозные: 399999/400000/400001 при LTV 50
  (включая `approved_limit`: запрошенная сумма при approve, 0 при review) и
  400001 при LTV 95 → reject. Ловит ошибки сборки: забыли передать пробег
  или порог в DI.
- `ApplicationValidatorTest` — пустой пробег (оба варианта) и `500001`.
- Feature-тестов нет и не добавляем (инфраструктуры `tests/Feature/` под
  endpoint+БД в репозитории нет) — проверка руками через `make test` + curl.

## 4. Риски

1. **Два порога пробега рядом** — главный риск. `vehicle.max_mileage_km`
   (500 000, валидация, 422) и новый `vehicle.review_mileage_km` (400 000,
   решение, review) живут в одной секции конфига. Зона 400 001–500 000
   меняет решение с approve на review; пробег > 500 000 остаётся ошибкой
   валидации, а НЕ review. Перепутать ключи или «улучшить» один порог
   вместо другого легко. Тесты `500001 → ValidationException` и
   `500000 → review` фиксируют границу между правилами.
2. **Приоритет правил** (Допущение 1): если заказчик имел в виду «ровно
   review» даже вместо reject — правка одна строка в `decide()` + переворот
   теста `400001 + LTV 95`. Пока приоритет не подтверждён, тесты фиксируют
   вариант плана.
3. **Смена сигнатуры `decide()`**: все места вызова/сборки должны
   обновиться синхронно — `AssessmentService.php:33`, `AppFactory.php:37`,
   `DecisionEngineTest.php:17`, `AssessmentServiceTest.php:27`. Пропуск
   даёт TypeError, `make test` ловит сразу.
4. **Соседняя LTV-граница**: в коде `ltv < approve_max` (60.0 → review), а
   docblock `DecisionEngine` (строка 10) и комментарий в `rules.php`
   (строки 38–41) утверждают `<=`. Существующее расхождение; задача его не
   чинит. При объединении условия approve с проверкой пробега границу легко
   незаметно сменить — новый тест `ltv 60.0 → review` фиксирует текущее
   поведение. Правку докблока `<=`/`<` не делаем (вне скоупа).
5. **Отклонение от code_map**: code_map называл минимальную точку вставки
   `AssessmentService::assess()` (пост-коррекция после `decide()`). План
   кладёт правило в `DecisionEngine`, чтобы логика решения оставалась в
   одном месте, а порог шёл из конфига тем же паттерном, что LTV-пороги.
   Альтернатива дешевле по диффу (4 файла вместо 7), но расщепляет решение
   на два класса и дублирует знание константы REVIEW в оркестраторе.
   Осознанное отклонение — вынести на ревью.
6. **Сохранённые решения**: решения уже записаны в таблицу `decisions` по
   старому правилу и задним числом не пересчитываются. Учебный проект,
   миграций нет и не планируется.
7. **Пустое поле формы**: фронтенд отправляет `Number('') === 0`, то есть
   незаполненный пробег доезжает до бэкенда как 0 км, а не как отсутствие
   ключа. Существующее поведение, задача его не меняет; отмечено тестом
   `'' → 0` на уровне валидатора.
8. **Сиды**: все 24 пробега в `db/seed.sql` — 20 000–296 000, ниже порога;
   ожидания по сидам не меняются, `db/**` не трогаем.

Не входит в задачу: сверка пробега с одометром по VIN-справочнику (CASE-08),
расчёт лимита по возрасту (LOAN-12), причина review в ответе API (контракт
ответа не меняется), фронтенд, схема и сиды БД, изменение валидационных
границ пробега, правка существующих докблоков про `<=` approve_max,
Feature-тесты.
