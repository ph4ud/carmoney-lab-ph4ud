## Как понято правило

- Пробег берётся из заявки (`mileage`, нормализуется валидатором в int 0..500000).
- «Плохой» пробег — два случая (REQ-MILEAGE-02/03): 0 км («нет данных», в том
  числе пустое поле формы, которое фронтенд отправляет как 0) и больше
  400 000 км.
- Если пробег от 1 до 400 000 включительно — решение не меняется (чистый
  LTV-расчёт, REQ-MILEAGE-01).
- Если пробег плохой — решение не `approve`: понижается до `review`;
  `reject` и `review` по LTV плохим пробегом не меняются (REQ-MILEAGE-04).
- Порог — число из `backend/config/rules.php`, не хардкод (конвенция AGENTS.md).

## 3. Тесты

Граничные значения по пробегу — отдельными строками (порог 400 000,
LTV-зоны: `< 60` approve, `60..85` review, `> 85` reject):

- `mileage 1` + LTV 50 → `approve` — нижняя граница зоны «пробег не меняет
  решение» (AC-MILEAGE-03)
- `mileage 399999` + LTV 50 → `approve` (правило не срабатывает, AC-MILEAGE-01)
- `mileage 400000` + LTV 50 → `approve` (граница включительно, AC-MILEAGE-02)
- `mileage 400001` + LTV 50 → `review` (понижение из approve, AC-MILEAGE-04)
- `mileage 500000` + LTV 50 → `review` (верх зоны правила и валидного
  диапазона, AC-MILEAGE-05)
- `mileage 0` + LTV 50 → `review` — 0 = «нет данных», включая пустое поле
  формы (AC-MILEAGE-06/07; Допущение 3)
- `mileage 400001` + LTV 95 → `reject` (приоритет reject — Допущение 1,
  AC-MILEAGE-10)
- `mileage 400001` + LTV 75 → `review` (решение и так review, не меняется,
  AC-MILEAGE-11)
- пустой пробег, ключа нет → `ValidationException` с ошибкой ключа `mileage`
  (AC-MILEAGE-08)
- пустой пробег, пустая строка `''` → валидно, нормализуется в `0` (поведение

## 4. Риски

1. **Два порога пробега рядом** — главный риск. `vehicle.max_mileage_km`
   (500 000, валидация, 422) и новый `vehicle.review_mileage_km` (400 000,
   решение, review) живут в одной секции конфига. Зона 400 001–500 000
   меняет решение с approve на review; пробег > 500 000 остаётся ошибкой
   валидации, а НЕ review. Перепутать ключи или «улучшить» один порог
   вместо другого легко. Тесты `500001 → ValidationException` и
   `500000 → review` фиксируют границу между правилами.
2. **Приоритет правил** (Допущение 1): подтверждён заказчиком (интервью,
   вопрос 4) — `reject` приоритетнее, правило гейтит только `approve`.
   Тесты `400001 + LTV 95 → reject` и `400001 + LTV 75 → review` фиксируют
   это (AC-MILEAGE-10/11). Если когда-нибудь понадобится «ровно review даже
   вместо reject» — правка одна строка в `decide()` + переворот этих тестов.
3. **Смена сигнатуры `decide()`**: все места вызова/сборки должны
   обновиться синхронно — `AssessmentService.php:33`, `AppFactory.php:37`,
   `DecisionEngineTest.php:17`, `AssessmentServiceTest.php:27`. Пропуск
   даёт TypeError, `make test` ловит сразу.
4. **Соседняя LTV-граница**: в коде `ltv < approve_max` (60.0 → review), а
   docblock `DecisionEngine` (строка 10) и комментарий в `rules.php`
   (строки 38–41) утверждают `<=`. Существующее расхождение; задача его не
   чинит. При объединении условия approve с проверкой пробега границу легко
   незаметно сменить — новая пара тестов `ltv 59.9 → approve` /
   `ltv 60.0 → review` фиксирует текущее поведение (AC-MILEAGE-12; границы
   85.0/85.01 уже пиниты провайдером). Правку докблока `<=`/`<` не делаем
   (вне скоупа).
5. **Отклонение от code_map**: code_map называл минимальную точку вставки
   `AssessmentService::assess()` (пост-коррекция после `decide()`). План
   кладёт правило в `DecisionEngine`, чтобы логика решения оставалась в
   одном месте, а порог шёл из конфига тем же паттерном, что LTV-пороги.
   Альтернатива дешевле по диффу (4 файла вместо 7), но расщепляет решение
   на два класса и дублирует знание константы REVIEW в оркестраторе.
   Осознанное отклонение — вынести на ревью.
6. **Сохранённые решения**: решения уже записаны в таблицу `decisions` по
   старому правилу и задним числом не пересчитываются. Учебный проект,
   миграций нет и не планируется.
7. **Пустое поле формы и явный 0**: фронтенд отправляет `Number('') === 0`,
   то есть незаполненный пробег доезжает до бэкенда как 0 км, а не как
   отсутствие ключа; бэкенд эти случаи не различает. По спеке
   (REQ-MILEAGE-03/07, AC-MILEAGE-06/07) любой 0 — «нет данных» → `review`,
   включая явно введённый. Валидация не меняется: `''` → 0 остаётся валидным
   (тест валидатора), а `0 → review` фиксируется тестами движка и сервиса.
   Фронтенд не трогаем.
8. **Сиды**: все 24 пробега в `db/seed.sql` — 20 000–296 000, ниже порога;
   ожидания по сидам не меняются, `db/**` не трогаем.

Не входит в задачу: сверка пробега с одометром по VIN-справочнику (CASE-08),
расчёт лимита по возрасту (LOAN-12), причина review в ответе API (контракт
ответа не меняется), фронтенд, схема и сиды БД, изменение валидационных
границ пробега, правка существующих докблоков про `<=` approve_max,
Feature-тесты.
