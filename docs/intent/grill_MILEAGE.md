## Вопрос 1. Граница порога 400 000 км

- Вопрос: пробег ровно 400 000 — правило не срабатывает (включительно) или уже понижает до review?
- Ответ: **Включительно** — `mileage <= 400000` решение не меняет; review с 400 001.
- Источник: ответ в интервью. Совпадает с plan_MILEAGE, Допущение 2.

## Вопрос 2. Пробег не указан

- Вопрос: нет ключа `mileage` / пустое поле — что делать? Сейчас: нет ключа → 422,
  пустое поле фронта доезжает как 0 км.
- Ответ: **нет ключа → 422, пустая строка с фронта → review**, пробег остаётся
  обязательным полем.
- Источник: ответ в интервью. Отличается от plan_MILEAGE, Допущение 3
  (там: пустая строка → 0 → обычный расчёт).

## Вопрос 3. Как технически отличить «нет данных» от 0 км

- Контекст из кода (проверено на интервью): `frontend/app.js:14` кастует поле через
  `Number('')` → пустое поле доезжает до бэкенда как `mileage: 0`, а не как пустая строка;
  `ApplicationValidator.php:43` различить `''` и `0` тоже не может (`(int)'' === 0`).
- Вопрос: что считать «нет данных → review»?
- Ответ: **0 км = нет данных → review**, только бэкенд, `frontend/**` не трогаем.
- Следствие: явный введённый 0 км тоже даст review; у правила два «плохих» случая —
  `0` и `> 400000`.
- Источник: ответ в интервью + код: `frontend/app.js:14`,
  `backend/src/Domain/ApplicationValidator.php:43`.

## Вопрос 4. Приоритет правила против LTV-решения

- Вопрос: по LTV reject (LTV > 85), пробег «плохой» (0 или > 400 000) — reject остаётся
  или правило перекрывает его review?
- Ответ: **Reject приоритетнее** — правило гейтит только approve; LTV-ветки и их порядок
  не меняются.
- Источник: ответ в интервью. Совпадает с plan_MILEAGE, Допущение 1.

## Вопрос 5. Границы scope

- Вопрос: подтверждается ли список «вне scope» из plan_MILEAGE?
- Ответ: **да, всё как в плане** — сверка с одометром по VIN (CASE-08), причина review

  докблоков `<=`/`<`, Feature-тесты, `frontend/**`, `db/**`.
- Источник: ответ в интервью.
