# intent_MILEAGE — пробег не больше 400 000 км, иначе решение review

- Дата: 2026-09-27. Автор: planner.
- Собрано после интервью Grill Me; лог — `docs/intent/grill_MILEAGE.md`.
- Источники требований: ответы заказчика в интервью (5 вопросов) и текущий код.

## 1. Замысел

Добавить в расчёт решения по заявке проверку пробега. «Плохой» пробег — 0 км
(нет данных о пробеге) или больше 400 000 км. При плохом пробеге заявка не может
получить `approve`: решение понижается до `review`. При пробеге от 1 до 400 000 км
решение считается как сейчас, только по LTV.

## 2. Зачем

Сегодня решение `approve` / `review` / `reject` зависит только от LTV: пробег
участвует лишь в проверке валидности заявки и на решение не влияет (код:
`backend/src/Domain/DecisionEngine.php` — на вход подаётся только LTV;
`backend/src/Domain/AssessmentService.php`). Заявка с пробегом больше 400 000 км
или без данных о пробеге может получить автоматический `approve`. Правило закрывает
этот случай: такие заявки `approve` не получают.

## 3. Constraints

- Порог — 400 000 км, граница включительно: пробег 400 000 и меньше (но больше 0)
  правило не срабатывает; «большой пробег» — 400 001 и выше. Источник: число 400 000 —
  формулировка задачи; включительность — ответ в интервью (вопрос 1).
- 0 км трактуется как «нет данных о пробеге» и тоже даёт `review`. Источник:
  ответ в интервью (вопросы 2–3).
- Правило гейтит только `approve`: `approve` + плохой пробег → `review`; `reject`
  плохим пробегом не смягчается; `review` остаётся `review`. Существующие пороги
  и порядок LTV-веток не меняются. Источник: ответ в интервью (вопрос 4).
- Пробег — обязательное поле: заявка без пробега невалидна и отклоняется с 422,
  а не `review`. Источник: ответ в интервью (вопрос 2); текущее поведение — код:
  `backend/src/Domain/ApplicationValidator.php` (отсутствие пробега — ошибка
  валидации), `backend/src/Http/ApplicationController.php` (ошибка валидации → 422).
- Пустое поле формы пробега доезжает до бэкенда как 0, отдельного случая «пустая
  строка» не возникает; фронтенд не меняется. Источник: код: `frontend/app.js`
  (`Number('') === 0`); ответ в интервью (вопрос 3).
- Валидационная граница пробега 500 000 км не меняется: пробег свыше 500 000 —
  невалидная заявка (422), не `review`; правило меняет решение только в зоне
  400 001–500 000 (и для 0). Источник: код: `backend/config/rules.php` (граница
  валидации пробега 500 000), `backend/src/Domain/ApplicationValidator.php`;
  ответ в интервью (вопрос 5 — валидационные границы вне scope).
- Контракт ответа API не меняется: решение по-прежнему `approve` / `review` /
  `reject` без обоснования. Источник: ответ в интервью (вопрос 5).

Сверка с исходной формулировкой задачи проведена: расхождения буквального
прочтения «иначе решение review» (перекрытие reject; пробег свыше 500 000)
закрыты ответами заказчика. Открытых вопросов нет.

## 5. Не входит

Подтверждено ответом в интервью (вопрос 5: «всё как в плане»):

- сверка пробега с одометром по VIN-справочнику (CASE-08);
- расчёт лимита по возрасту авто (LOAN-12);
- причина `review` в ответе API — контракт ответа не меняется;
- пересчёт уже сохранённых решений;
- фронтенд;
- схема и сиды БД;
- изменение валидационных границ пробега (500 000 км);
- правка существующих докблоков про LTV-границу approve;
- Feature-тесты.
