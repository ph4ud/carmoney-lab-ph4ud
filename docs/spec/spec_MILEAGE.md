# spec_MILEAGE — пробег не больше 400 000 км, иначе решение review

- Дата: 2026-09-27. Автор: spec (Kilo).
- Источник требований: `docs/intent/intent_MILEAGE.md`; лог интервью —
  `docs/intent/grill_MILEAGE.md`; текущий код — по ссылкам ниже.
- Проверяемость — на уровне расчёта решения по заявке (как в intent §2) и
  HTTP-поведения API заявки.

## 1. Входит / не входит

Входит:

- новое правило в расчёте решения по заявке: при «плохом» пробеге — 0 км
  («нет данных») или 400 001 км и выше — решение `approve` недоступно,
  итоговое решение — `review` (REQ-MILEAGE-02…04, 09);
- трактовка 0 км как «нет данных о пробеге» (REQ-MILEAGE-03);
- неизменное поведение, зафиксированное требованиями: обязательность поля
  `mileage` (REQ-MILEAGE-06), валидационная граница 500 000 км
  (REQ-MILEAGE-08), пороги LTV и порядок LTV-веток (REQ-MILEAGE-05),
  контракт ответа API (REQ-MILEAGE-10).

Не входит (intent §5, подтверждено ответом в интервью, вопрос 5: «всё как в плане»):

- сверка пробега с одометром по VIN-справочнику (CASE-08);
- расчёт лимита по возрасту авто (LOAN-12);
- причина `review` в ответе API — контракт ответа не меняется;
- пересчёт уже сохранённых решений;
- фронтенд;
- схема и сиды БД;
- изменение валидационных границ пробега (500 000 км);
- правка существующих докблоков про LTV-границу approve;
- Feature-тесты.

## 2. Требования (REQ-MILEAGE-NN)

Каждое REQ — одно проверяемое утверждение с источником. Каждый REQ опирается
на intent §1/§3 (Constraints) или на ответ интервью из `grill_MILEAGE.md`;
требований сверх intent нет.

### REQ-MILEAGE-01
При пробеге от 1 до 400 000 км включительно решение по заявке определяется
только действующими LTV-правилами — правило пробега решение не меняет.
Источник: intent §1, §3 (п.1); числа: 400 000 — формулировка задачи,
включительность — ответ в интервью, вопрос 1; нижняя граница 1 — intent §1.

### REQ-MILEAGE-02
При пробеге 400 001 км и выше заявка не может получить решение `approve`:
если по действующим LTV-правилам решение `approve`, итоговое решение — `review`.
Источник: формулировка задачи; intent §1, §3 (п.1); ответ в интервью, вопрос 1.

### REQ-MILEAGE-03
Пробег 0 км трактуется как «нет данных о пробеге» и обрабатывается так же,
как пробег из REQ-MILEAGE-02: `approve` недоступен, итоговое решение — `review`.
Источник: intent §3 (п.2); ответ в интервью, вопросы 2–3.

### REQ-MILEAGE-04
Правило гейтит только `approve`: если по LTV решение `reject`, оно остаётся
`reject`; если `review` — остаётся `review`.
Источник: intent §3 (п.3); ответ в интервью, вопрос 4.

### REQ-MILEAGE-05
Действующие пороги LTV — `approve_max` 60.0 и `review_max` 85.0 — и порядок
LTV-веток решения не меняются.
Источник: intent §3 (п.3); ответ в интервью, вопрос 4; числа — код:
`backend/config/rules.php:44-45`; ветки — `backend/src/Domain/DecisionEngine.php:30-41`.

### REQ-MILEAGE-06
Пробег — обязательное поле заявки: если ключ `mileage` отсутствует, заявка
невалидна и отклоняется с HTTP 422, а не понижается до `review`.
Источник: intent §3 (п.4); ответ в интервью, вопрос 2; код:
`backend/src/Domain/ApplicationValidator.php:43-46` (отсутствие ключа → ошибка
валидации по полю `mileage`), `backend/src/Http/ApplicationController.php:29-31,60-62`
(ошибка валидации → 422).

### REQ-MILEAGE-07
Незаполненное поле пробега формы доезжает до бэкенда как `mileage = 0`
(`Number('') === 0`) и обрабатывается по REQ-MILEAGE-03; фронтенд не меняется,
отдельный случай «пустая строка» не выделяется.
Источник: intent §3 (п.5); код `frontend/app.js:14`; ответ в интервью, вопрос 3.

### REQ-MILEAGE-08
Валидационная граница пробега 500 000 км не меняется: заявка с пробегом
500 001 км и выше невалидна и отклоняется с HTTP 422, а не `review`.
Источник: intent §3 (п.6); код: `backend/config/rules.php:23`
(`max_mileage_km` = 500000), `backend/src/Domain/ApplicationValidator.php:43-45`;
ответ в интервью, вопрос 5.

### REQ-MILEAGE-09
Зона действия правила пробега — валидные заявки с пробегом 0 км или из
диапазона 400 001–500 000 км; заявки с пробегом 500 001 км и выше до правила
не доходят (REQ-MILEAGE-08).
Источник: intent §3 (п.6); ответ в интервью, вопрос 5; числа — как в
REQ-MILEAGE-02 и REQ-MILEAGE-08.

### REQ-MILEAGE-10
Контракт ответа API не меняется: `decision` принимает значения
`approve` / `review` / `reject`; поле с причиной решения в ответе отсутствует.
Источник: intent §3 (п.7); ответ в интервью, вопрос 5; текущий состав полей —
код `backend/src/Http/ApplicationController.php:44-50,64-69`.

## 3. Критерии приёмки (AC-MILEAGE-NN)

Формат Given / When / Then; у каждого — ссылка на REQ. Все заявки в AC
считаются валидными, кроме случаев с HTTP 422. Примеры LTV: 50 — approve-зона
(LTV < 60.0), 75 — review-зона (60.0 ≤ LTV ≤ 85.0), 95 — reject-зона
(LTV > 85.0); зоны — код `backend/config/rules.php:44-45`,
`backend/src/Domain/DecisionEngine.php:32-40`.

- **AC-MILEAGE-01** (REQ-MILEAGE-01). Given: пробег 399 999, LTV 50. When:
  рассчитывается решение. Then: `decision = approve` — правило не срабатывает.
- **AC-MILEAGE-02** (REQ-MILEAGE-01). Given: пробег 400 000, LTV 50. When:
  рассчитывается решение. Then: `decision = approve` — граница включительно.
- **AC-MILEAGE-03** (REQ-MILEAGE-01). Given: пробег 1, LTV 50. When:
  рассчитывается решение. Then: `decision = approve` — нижняя граница зоны
  «пробег не меняет решение».
- **AC-MILEAGE-04** (REQ-MILEAGE-02). Given: пробег 400 001, LTV 50. When:
  рассчитывается решение. Then: `decision = review` — понижение с approve.
- **AC-MILEAGE-05** (REQ-MILEAGE-02, REQ-MILEAGE-09). Given: пробег 500 000,
  LTV 50. When: рассчитывается решение. Then: заявка валидна,
  `decision = review` — верхняя граница зоны действия правила.
- **AC-MILEAGE-06** (REQ-MILEAGE-03). Given: пробег 0, LTV 50. When:
  рассчитывается решение. Then: `decision = review` — 0 = «нет данных»,
  независимо от того, введён 0 явно или поле оставлено пустым.
- **AC-MILEAGE-07** (REQ-MILEAGE-07). Given: поле пробега в форме не заполнено,
  фронтенд отправляет его как `Number('') = 0`, остальные поля валидны, LTV 50.
  When: заявка отправляется на расчёт. Then: заявка валидна,
  `decision = review`; изменения фронтенда не требуется.
- **AC-MILEAGE-08** (REQ-MILEAGE-06). Given: в заявке нет ключа `mileage`,
  остальные поля валидны. When: заявка отправляется на расчёт. Then: HTTP 422,
  ошибка валидации привязана к полю `mileage`; решение не рассчитывается
  и в `review` не понижается.
- **AC-MILEAGE-09** (REQ-MILEAGE-08). Given: пробег 500 001, остальные поля
  валидны. When: заявка отправляется на расчёт. Then: HTTP 422 — ошибка
  валидации, а не `review`.
- **AC-MILEAGE-10** (REQ-MILEAGE-04). Given: пробег 400 001, LTV 95. When:
  рассчитывается решение. Then: `decision = reject` — плохой пробег не смягчает
  reject.
- **AC-MILEAGE-11** (REQ-MILEAGE-04). Given: пробег 400 001, LTV 75. When:
  рассчитывается решение. Then: `decision = review` — review остаётся review.
- **AC-MILEAGE-12** (REQ-MILEAGE-05). Given: пробег в зоне 1–400 000
  (например 100 000 — правило не действует). When: рассчитывается решение при
  LTV 59.9 / 60.0 / 85.0 / 85.1. Then: `approve` / `review` / `review` / `reject`
  — как в текущем коде: пороги и порядок LTV-веток не изменились.
- **AC-MILEAGE-13** (REQ-MILEAGE-10). Given: валидная заявка с плохим пробегом
  (например 400 001 при LTV 50). When: API возвращает ответ. Then:
  `decision = review`; поле с причиной решения в ответе отсутствует; состав
  остальных полей ответа — как в текущем коде
  `backend/src/Http/ApplicationController.php:44-50,64-69`.

Покрытие границ: порог правила — 399 999 (AC-01), 400 000 (AC-02),
400 001 (AC-04); пустой и неизвестный пробег — AC-06 (0 → review),
AC-07 (пустое поле формы → 0 → review), AC-08 (нет ключа → 422);
валидационная граница — 500 000 / 500 001 (AC-05 / AC-09).
